Troubleshooting

Fixes for the problems people run into most. When in doubt, two places tell you more: the plugin's publish report, and the server's log (docker compose logs kvist).

Setting up

docker compose pull says “denied” or “unauthorized”

The kvist image is in GitHub's container registry. If it says access is denied, the image isn't public. If you run your own fork, open your GitHub profile → Packages → kvist → Package settings → Change visibility → Public. Or log in on the server with docker login ghcr.io, using a GitHub token with the read:packages permission.

The site doesn't load, or the browser warns about the certificate

  • Check that your domain points at the server: dig +short garden.example.com should print its IP address.
  • Ports 80 and 443 must be open. Caddy needs port 80 to get a certificate.
  • Look at Caddy's log: docker compose logs caddy.
  • With Cloudflare's proxy on, set SSL/TLS to Full (strict). If Caddy can't get a certificate, switch the DNS record to DNS only (grey cloud) until it has one, then turn the proxy back on.

The site says “404 not found”

Nothing has been published yet. Publish from Obsidian, and the site appears. If you have published, check that serve = true is set for the site in kvist.toml.

The plugin doesn't show up in Obsidian

  • The three files must be directly in <vault>/.obsidian/plugins/kvist/: main.js, manifest.json and styles.css. A common mistake is one folder too many (plugins/kvist/kvist/) after unzipping.
  • Download kvist-plugin.zip again if a file is missing.
  • Turn off Restricted mode under Settings → Community plugins, then press the reload button next to Installed plugins.

“Test” in the plugin fails

MessageWhat to check

Publishing

A note isn't on the site

  • Open the note and run kvist: Toggle publish for current note. If a rule keeps it private (an excluded folder, the #private tag), the message says which. Run the command again if you didn't mean to change it.
  • Check the folder name's letter case: always_public_folders = ["Kvist"] doesn't match a folder called kvist.
  • Pages can be cached for up to a minute; reload after that.

Some links are plain text on the site

The note they point to isn't published, or doesn't exist. That's by design: it keeps private notes hidden. The publish report lists them. Markdown-style links work too, but their path is read from the linking note's folder: [text](Bread.md) from Kvist/Ideas/ looks for Kvist/Ideas/Bread.md first, then any note called Bread (see Writing notes).

An image or file is missing

  • It sits in an excluded folder (the report lists these under Attachments in excluded folders). Move it, or set an attachment folder outside the excluded ones in Obsidian's Files and links settings.
  • Its file type isn't allowed, or it is over 50 MiB. See attachment_extensions and limits.

“The site build failed”

The live site keeps showing the last good version. The message says what's wrong. The most common causes:

  • Two notes would get the same address, for example My note.md and My Note!.md, or a note's permalink clashes with another. The message names both; rename one.
  • A link or embed to a private note, when unpublished_links or unpublished_embeds is set to "error".

“The server has newer content than this device” (◆)

Another device published changes this device hasn't received yet, and publishing now would put older notes back. Let your vault finish syncing, then run Publish now. It shows which notes are affected and asks before going ahead. See More than one device.

An old link to a renamed note shows “Nothing grows here”

The server redirects a renamed or moved note's old address when it can tell which note it became: the same file at a new place, the same text, or the only new note with the same file name. It can't when the note was renamed and edited and another new note has its new file name, or when the note was renamed while it was private. Publishing after each rename, rather than many renames at once, gives it the best chance. Redirects start with the first publish after you update the server; renames before that aren't known.

The site's icon didn't change

Browsers keep site icons for a long time. Check the icon in a private window, or open the page's address with ? at the end. The favicon must be an image the server publishes: a PNG or SVG in a folder that isn't excluded.

A page is still visible after I unpublished it

Browsers and CDNs may keep a page for up to 60 seconds. With Cloudflare, set up the cache purge so it disappears immediately. If a search engine already indexed it, it can take that search engine some time to notice.

Settings

My changes to kvist.toml did nothing

Restart kvist (docker compose restart kvist), then publish again. If kvist doesn't come back up, the file has a mistake; docker compose logs kvist says where.

My changes to the settings note did nothing

  • The note must be called exactly _site.md, with the underscore.
  • Publish after editing it: the settings go up with your notes.
  • An empty property keeps its default; write a value to change something.
  • Colors start with # and must be in quotes: accent: "#8a4f9e". Without quotes, the rest of the line is read as a comment.
  • Open the publish report. A setting that can only be set on the server, a home note that isn't published, or a menu link to a private note shows up there as a warning.
  • For groups, at least one published note must carry each tag.

“found 2 settings notes”

Only one note may be called _site.md. The message names both; delete or rename one.

Still stuck?

Open an issue on GitHub with what you did, what you expected and the error message. Remove tokens and private note names before posting logs.
